# 反模式

[English](anti-patterns.md) | [简体中文](anti-patterns.zh-CN.md)

这些模式描述常见结果，不是某个仓库的具体禁令。示例使用通用功能名称，避免案例本身成为新的全局限制。

## 1. 删除膨胀

**表现：** 小规模删除却产生大型验证器、检测器、拒绝列表或测试集合。

**危害：** diff 保护的是被放弃的历史，而不是支持的契约，增加维护成本，并可能阻碍未来合理变更。

**合理处理：** 删除不支持的实现。只保留支持行为或可信重复回归所需要的测试。

## 2. 对话型 PR 文案

**表现：** PR 标题和正文叙述 Agent 之前的错误、用户纠正过程和被放弃方案。

**危害：** 审查者需要从过程描述中重建最终结果，仓库历史被临时对话绑定。

**合理处理：** 描述最终行为、用户可见影响、相关文件、验证结果和必要的长期权衡。

## 3. 宣布不存在的功能

**表现：** 界面、帮助页或公开文档告诉用户某个已删除能力不存在。

**危害：** 产品表面暴露实现历史，制造用户原本没有的问题。

**合理处理：** 删除过时表面。只有当限制影响用户决策或运维时，才记录它。

## 4. 历史注释残留

**表现：** 注释解释一个已经被否决的方案，而当前代码并不需要该解释。

**危害：** 后续维护者可能把放弃的理由误认为当前约束。

**合理处理：** 保留解释当前非直观约束的注释，删除只叙述纠错过程的注释。

## 5. 局部纠正变成全局偏好

**表现：** 一个输出或组件的决定被写入全局记忆，或用于过滤无关工作。

**危害：** 上下文相关性下降，用户失去对未来选择的控制。

**合理处理：** 除非用户明确要求持久化或已有项目规则要求，否则保持任务级作用域。

## 6. 反向测试

**表现：** 测试主要断言被放弃的概念永远不能出现，而不是验证产品应支持的行为。

**危害：** 测试编码的是历史，可能阻止未来合法需求，却没有保护产品契约。

**合理处理：** 测试支持行为、可信回归、安全边界和兼容性契约。

## 7. 永久免责声明

**表现：** 文档充满项目“不做什么”的说明，而这些缺失并不是用户关心的限制。

**危害：** 负面列表变成嘈杂的第二份规格，反而让被否决概念更显眼。

**合理处理：** 描述目标能力，只在帮助用户或维护者做决定时说明重要边界。

## 8. 纠错递归

**表现：** Agent 增加一条规则防止前一条规则再次出现，然后继续增加规则保护这条规则。

**危害：** 指令层级变得难以解释，原始产品任务被流程控制覆盖。

**合理处理：** 保留一个简洁原则，结合任务作用域和最终 diff 审查。
