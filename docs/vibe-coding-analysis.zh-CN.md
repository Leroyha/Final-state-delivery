# Vibe Coding 与最终状态边界

[English](vibe-coding-analysis.md) | [简体中文](vibe-coding-analysis.zh-CN.md)

## AI 编写代码后发生了什么变化

Vibe Coding 是一种 AI 辅助开发方式：人描述目标，Agent 负责探索、编辑、测试和解释实现。人仍然负责产品意图和验收边界，Agent 承担大量机械工作。

这改变了失败的形态。在手工开发中，被否决的设计通常会随着工作树变化而消失，除非有人刻意记录。在 Agent 工作流中，被否决设计仍然存在于控制下一步行为的对话里，同一上下文随后可能影响源代码、测试、文档和发布文字。

## Agent 循环

```text
🟦 请求 → 🟩 规划 → 🟨 检查 → 🟧 实现 → 🟪 测试 → 🟫 解释 → 🔄 修订
                                           ↑                |
                                           └────── 回到检查 ─┘
```

当每次循环都让实现更接近当前契约时，循环是有价值的。当早期解释被当成后续需求时，循环就会产生噪声。

## 四条边界

### 产品边界

仓库和应用应暴露支持的行为、长期约束和必要理由，不应因为某个提议曾经出现过，就向产品暴露被放弃的方案。

### 任务边界

当前请求拥有自己的验收标准。一个任务的纠正不应在没有明确指示时改写无关任务、未来推荐或用户画像。

### 记忆边界

长期记忆应包含稳定事实和明确要求保存的偏好。临时纠正、失败假设和被否决实现属于工作上下文，应随任务结束而失效。

### 审查边界

最终 diff、测试结果、渲染界面和用户可见文字才是完成证据。Agent 的自信说明不能代替作用域和比例审查。

## 实用工作流

### 1. 写出正向任务契约

说明完成后应该存在什么，列出影响的界面、输入、输出和验收标准，并把局部约束放在对应任务旁边。可使用 [`../templates/task-spec.zh-CN.md`](../templates/task-spec.zh-CN.md)。

### 2. 分离探索和交付

允许 Agent 在规划阶段考虑不同方案，但在实现前明确交付目标。最终任务规格应包含选定要求，而不是所有被放弃的可能性。

### 3. 要求比例合理的变更

Agent 应先检查现有实现，再做满足契约的最小连贯修改。删除或简化任务不应在没有独立理由时产生大型防御子系统。

### 4. 验证行为和作用域

运行项目正常检查，然后检查 diff 是否存在历史用语、无关防护、无关文件和新的持久化偏好。这是验收的一部分，不是可选润色。

### 5. 干净结束任务

最终交接应总结结果行为、修改文件、已运行的验证和真实限制，不应复述完整对话或宣传被放弃方案。

## 不应误解为“禁止解释”

本规范不要求删除所有注释或说明。安全、兼容性、迁移、法律、运营和非直观业务约束，在未来维护者确实需要时应保留。要求的是相关性和作用域，而不是完全沉默。
