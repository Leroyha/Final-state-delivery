# LLM 与上下文分析

[English](llm-analysis.md) | [简体中文](llm-analysis.zh-CN.md)

本文件解释为什么当前语言模型工作流中可能出现被否决上下文泄漏。以下内容使用限定性表述，因为一次输出通常由模型、提示、上下文、工具和记忆机制共同影响，不能把所有案例归因于单一原因。

## 1. 否定指令仍会激活其对象

为了理解“不要包含 X”，模型需要表示这条指令及其提到的概念。即使目标是省略，概念本身仍然存在于提示文本中。重复提及被否决概念，会增加它在上下文中的文本存在感和继续生成相关内容的机会。

这与人类常说的“不要想大象”现象有相似之处，但不能直接把人类认知实验等同于神经语言模型。更稳妥的工程结论是：重复的否定措辞仍然属于上下文，而上下文选择是模型行为的重要因素。明确描述期望的最终状态，通常比反复列举禁令更干净。

## 2. 指令遵循会鼓励可见的理解证据

经过指令微调的模型通常被优化为产生人类认为有帮助、相关且遵循要求的回答。在聊天中，简短确认可能很有用；在编码工作流中，同样的倾向可能变成过度确认：模型把纠正重复写入计划、注释、测试名称、PR 描述和记忆。

这不是模型的主观动机，而是提示、示例、奖励信号和当前对话共同形成的生成模式。实用边界是：确认可以存在于工作交流中，仓库只保留运行和维护最终系统所必需的信息。

## 3. 上下文窗口不是需求数据库

长对话同时包含需求、例子、假设、被否决提议、情绪强调、工具输出和临时调试状态。如果没有外部分类和筛选机制，这些内容都会以类似的上下文形式呈现。更多上下文有时能提高召回，但也会降低优先级清晰度。

长上下文研究表明，信息位置和检索条件会影响模型表现。因此，当前任务和验收标准应放在紧凑且权威的任务规格中，而不应要求模型把整段探索性对话永久当作规格。

## 4. 纠错历史可能被误认为长期要求

“从当前页面删除它”和“以后所有项目都不要使用它”具有不同生命周期，但自然语言常常省略这个生命周期。为了保持帮助性，Agent 可能推断出更宽泛的规则，尤其是在存在记忆工具或仓库规则文件时。

典型的错误升级链是：

```text
局部纠正 -> 任务要求 -> 仓库规则 -> 用户偏好
```

最终状态交付要求显式判断这个升级过程。除非用户明确要求持久化或已有项目规则要求，否则默认保持任务级作用域。

## 5. 被否决想法会形成生成吸引点

当对话反复把目标结果与被否决方案进行对比时，模型会获得更多继续生成这种对比结构的机会。因此，即使争论已经结束，最终回答仍可能长篇解释不存在的功能。

解决方案不是建立更大的词语黑名单，而是提供正向的最终状态描述，并用最终 diff 检查把无关残留视为缺陷。

## 6. 补偿性复杂度不等于可靠工程

模型可能在纠正之后增加防护结构，因为额外结构看起来像可靠性的证明。只有当它保护支持的行为或可信的重复风险时，这种结构才有理由存在。一次误解并不自动需要检测器、拒绝列表、验证器或永久回归测试。

可以使用一个工程问题判断：

> 如果看不到历史对话，这段代码是否仍然能由当前产品契约、安全要求、兼容性要求或可信回归来证明合理？

如果不能，就应考虑删除或简化。

## 7. 记忆系统会放大生命周期错误

外部记忆改变了风险。一条错误记忆的生命周期比聊天消息更长，并可能影响后续无关任务。记忆应保存稳定且经过用户授权的偏好和项目事实，而不应成为事故日志或历史纠正相关词汇的列表。

## 8. 证据支持的结论

现有研究和工程经验支持以下谨慎结论：提示内容、顺序和重复会影响生成；指令微调鼓励模型遵循并经常解释要求；长上下文检索并不完美；外部记忆可能跨任务携带过时信息；作用域和比例仍需要人工审查。

这些证据不支持“每个否定指令都会提高某个词的内部注意力权重”或“一条短规则可以完全控制所有模型”的绝对说法。

## 9. 工程含义

1. 用正向、具体的语言描述目标结果。
2. 为任务级限制标记明确作用域和生命周期。
3. 不把被否决方案写入持久化产物。
4. 把最终 diff、测试和用户可见文案作为完整系统快照审查。
5. 只有在明确授权或已有项目规则支持时写入长期记忆。
6. 优先测试支持的行为，而不是测试被放弃的历史。
