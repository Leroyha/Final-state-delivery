# 最佳实践

[English](best-practices.md) | [简体中文](best-practices.zh-CN.md)

## 给任务提出者

### 描述正向结果

先说明任务完成后应该存在什么，列出影响的界面、输入、输出和验收标准。把局部约束放在它所管辖的任务旁边。

### 明确持久化

当偏好或规则需要跨任务保留时，使用清晰表达，例如“把这条加入仓库规范”或“以后所有任务都使用这个偏好”。没有这类信号时，纠正默认只在当前任务有效。

### 让证据贴近契约

如果安全、法律、兼容性、迁移或运营理由必须长期保留，就写入合适的项目文档。不要把一个容易记住的事故当作长期要求的替代品。

## 给 Agent 维护者

### 分离工作上下文和持久上下文

对话、草稿计划、仓库规范、用户偏好和记忆应有不同生命周期。支持写入记忆的系统，应让状态转换明确可见。

### 优先使用正向目标

把目标状态、支持行为和验收标准作为主要任务表示。反复把被否决概念写成黑名单，可能使概念保持高显著性，并让黑名单本身成为意外需求。

### 要求最终状态输出

要求 Agent 报告结果行为、修改文件、验证和真实限制，不要求复述每个被放弃方案。

### 保留合理理由

本规范不是删除所有注释或文档的指令。防止安全回归、保持兼容、解释迁移或说明非直观业务规则的内容应保留。

## 给审查者

按以下顺序检查：

1. 行为是否符合当前任务？
2. 所有修改文件是否相关？
3. 简化任务是否仍然简单，还是新增了无依据的机制？
4. 注释、测试、文档和 PR 文案是否描述当前行为？
5. 局部约束是否未经授权变成了全局偏好或项目规则？
6. 保留的理由是否确实有利于后续维护？

## 给记忆和规则文件

使用最小的持久化表述记录稳定规则。不要保存被否决实现、禁止概念清单或一次性纠正。项目规则文件保存项目要求，用户记忆保存用户授权偏好，任务笔记随任务结束而失效。

## 给测试

测试是产品和工程契约。只有在保护支持行为、可信回归、安全边界或兼容承诺时才增加测试。唯一目的为纪念被放弃想法的测试，通常说明历史已经泄漏进契约。
