# 问题定义：被否决上下文泄漏

[English](problem-statement.md) | [简体中文](problem-statement.zh-CN.md)

## 定义

**被否决上下文泄漏**是指：已经放弃的想法、被否决的实现、纠错过程或临时对话限制，在没有明确作用域的情况下继续进入最终产物，或影响后续无关任务。

最终产物可以是源代码、测试、注释、界面文案、设计文档、提交信息、PR 描述、Agent 记忆或后续推荐。重点不在于某个词是否出现，而在于已经失效的工作上下文是否改变了产品、仓库或无关决策。

## 典型案例

有人让 AI 准备一盘简单的番茄炒蛋，AI 却加入了无关的菜品。用户要求删除后，AI 虽然移除了实现，却在 PR 标题、注释、测试、验证器、文档或记忆中不断保留这个被否决的想法。结果是错误内容从产品中消失，却在开发产物中变得更加显眼。

这个案例展示了四种信息的区别：

- 对话：包含提议、修正和探索过程；
- 规格：包含当前有效的需求；
- 产品：描述系统当前支持的行为；
- 记忆或项目规则：只保存明确需要长期有效的信息。

## 可观察表现

### 1. 删除导致无依据的代码增长

删除功能后增加检测器、拒绝列表、验证器或大量测试，而这些内容唯一的作用是防止一次被放弃的实现重新出现。

### 2. PR 描述变成对话记录

标题或正文重点描述 Agent 之前犯了什么错误、用户如何纠正，以及哪些方案被放弃，导致审查者难以确认最终结果。

### 3. 产品文案宣布某功能不存在

界面、帮助页或公开文档专门说明某个已经删除的功能不存在，让用户接触到与其无关的实现历史。

### 4. 局部纠正变成全局偏好

一个组件、一次任务或一种输出格式的决定，被泛化成用户画像、仓库级禁令或无关推荐规则。

### 5. 记忆记录事故而不是稳定规则

记忆文件保存了临时纠正、被否决的概念或负向偏好，而用户从未要求这些内容长期保存。

### 6. 防御性编程变成纠错展示

代码复杂度增加的主要目的，是证明 Agent 理解了纠正，而不是保护支持的行为、安全边界、兼容性契约或可信的回归风险。

## 为什么重要

这类问题会造成更大的 diff、更高的维护成本、误导性文档、被历史绑架的测试、后续变更受限、记忆相关性下降，以及对 AI 计划和解释的信任下降。

Vibe Coding 中一个对话经常同时推动规划、实现、测试、文档和发布说明，因此一次误解很容易复制到多个层面。

## 作用域模型

| 作用域 | 典型生命周期 | 合理内容 |
| --- | --- | --- |
| 消息 | 一次回复 | 当前回答的措辞调整 |
| 任务 | 当前请求 | 当前功能的验收要求 |
| 组件 | 指定模块或页面 | 组件契约要求的行为 |
| 仓库 | 有文档记录的项目规则 | 稳定架构、安全或发布约定 |
| 用户偏好 | 跨任务的未来工作 | 用户明确要求长期使用的偏好 |

Agent 不应在没有证据或明确指示的情况下，把小作用域信息升级到大作用域。

## 解决方向

最终状态交付使用四个检查：

1. **状态：** 产物是否描述修改后真实存在的内容？
2. **作用域：** 约束是否只作用于被证明需要它的范围？
3. **持久化：** 长期保存是否得到明确授权或已有项目规则支持？
4. **比例：** 实现复杂度是否服务于支持的行为或可信风险？

这些检查是审查标准，不要求为每次对话错误创建新的检测器或永久测试套件。
